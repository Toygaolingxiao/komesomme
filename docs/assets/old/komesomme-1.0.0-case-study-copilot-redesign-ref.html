課題定義

比較できない味の言葉を扱う

産地や価格だけでは決め切れない米選びを、甘み、粒感、料理との相性として比較可能にする。ここで定めた範囲が、以降のデータ構造と画面の判断基準です。

実験の対象を、狭く正確に決める

1.0.0 の中心は、今夜の料理と好みに合う米を選ぶことです。広げる前に、判断が必要な境界を明確にしました。

実験仮説

料理や口感の言葉から候補を絞る体験は、産地や価格だけを並べる選択よりも比較の軸を増やせる。

設計上の境界

推薦は銘柄単位です。産年、精米日、水量、炊飯器までを含む SKU 単位の味保証には踏み込みません。

購入導線の位置づけ

楽天などへの直リンクは実装済みです。次は推薦後の行動とカタログ更新コストを観測し、投資判断につなげます。

味わい地図を、入力装置にする

ベクトル検索を前面に出すのではなく、甘みと粒感の二次元盤で好みを指せるようにしました。

この盤面で動くのは探針だけです。銘柄座標はカタログの固定値で、近い4銘柄を同じ計算で強調します。

端末内で完結 地図操作は API を呼びません。二次元距離だけで候補を更新します。
上位4件を同じ粒度で表示 相談経路と候補数を揃え、画面ごとの選び直しを増やしません。

探針をドラッグ、タップ、または矢印キーで動かすと、近い銘柄が更新されます。

ほどける 粒立ち すっきり 甘みふくよか

    各銘柄を選択しても探針の位置は更新できます。表示される順位はこのデモ内の二次元距離に基づきます。

    相談経路と地図経路を分ける理由

    地図は低遅延な探索のための UI です。料理を文章で相談する場合のみ、同じモデル版で埋め込みを作り、pgvector で候補を取得します。二つを無理に融合せず、入力に合う経路を選びます。

    差分は、モデルではなく正本にある

    候補の根拠をカタログと規則に残すことで、入力の自由さと説明可能な出力を両立させます。

    推薦の正本

    Git に置いた構造化カタログ

    甘みと粒感は相対座標、料理相性と向かない組み合わせは人手のメモとして持ちます。

    地図の座標 味わいを端末内で比較するための固定値です。
    料理相性の規則 候補を並べ替えず、カード上の理由を組み立てます。
    更新可能な運用単位 validate:rice で必須フィールドとスコア範囲を検査します。
    推薦後の行動 主要な観測は shop_click です。
    入口の使われ方 consult_submit と料理別入口をページ型で見ます。
    再訪の手掛かり share、LINE、revisit を次の体験設計に接続します。
    カタログの粒度と、商流の観測範囲

    推薦は銘柄単位で、袋ごとの産年や精米日を保証するものではありません。購入導線はアフィリエイト直リンクを含みます。shop_click と管理画面の成果を突合し、利用の信号と更新工数を合わせて次の事業仮説を判断します。

    採用は、トレードオフの記録

    一人体制で運用できる境界と、推薦の一貫性を守ることを優先して選びました。

    見送り 異モデルの混在比較

    再計算の原則を見る

    provider を切り替えるときは、seed でカタログを全量再計算します。RPC は embedding_model を必須にして、同じ版だけを照合します。

    推薦
    採用 座標と意味検索の二経路

    地図は低遅延、相談だけが意味検索を使います。

    見送り 操作のたびに LLM

    候補決定を生成の振る舞いに依存させません。

    出力契約を見る

    地図も相談も上位4件で返します。1.0.0 では diversity rerank を対象にせず、近い候補が似る可能性は次の評価対象です。

    データ投入
    採用 TS catalog → seed:rice

    Git を正本にし、DB は配信用の控えにします。

    見送り 別言語の常設スクレイパ

    日常の保守対象を増やしません。

    更新の原則を見る

    埋め込みを含むカタログは、正本の変更から検証と seed を通して更新します。銘柄数を増やす前に、100銘柄あたりの工数を見積もります。

    購入導線
    採用 検索 CTA と楽天直リンク

    比較の直後に購入先へ進める出口を置きます。

    見送り 全モール API の必須化

    規約対応と運用負荷を先に増やしません。

    次の判断を見る

    shop_click と成果の突合、カタログ更新コストを観測し、購入導線を拡張する価値を判断します。

    経路を分けると、説明も運用も明快になる

    地図と相談は同じ画面に見えても、遅延、権限、失敗時の振る舞いが異なるため別の経路として設計しています。

    地図の経路: 探針の操作はブラウザ内の二次元距離で完結します。サーバと外部モデルを経由しないため、探索の手触りを保てます。

    順位は決定的に、言葉は補助的に

    候補を作る処理と、利用者へ説明する処理を分離し、失敗時にも候補が残るパイプラインにしています。

    入力

    銘柄名か、料理の一文かを受け取る

    銘柄名に直接ヒットすればその候補を使い、それ以外は同じモデル版で埋め込みを作る準備に進みます。

    名前ヒット / 相談文

    地図の順位

    甘みと粒感の二次元距離を端末内で計算します。表示は上位4件で、意味検索を混ぜません。

    相談の順位

    銘柄名ヒット、またはモデル版を揃えた pgvector の類似度で決めます。相性規則は順位を変更しません。

    生成が失敗したときの振る舞い

    LLM が担当するのは案内文です。埋め込みは5秒で打ち切り、案内文が書けない場合も、決定済みの上位4件と規則から作った理由を返す経路を保持します。

    公開は、一つの完了ではなく通過条件の集合

    データ、意味検索、地図、公開境界を順に閉じ、確認可能な状態だけを次の工程へ渡しました。

    データ基盤

    RiceSource から構造化カタログを作り、80件以上を MVP 表示確認の下限に置きました。現在は約106件を validate:rice で検査します。

    公開時に確認した運用条件

    CI で lint、型検査、試験、ビルドを通し、公開環境は origin/main からデプロイします。埋め込みと照合 RPC は一般公開せず、相談 API には日次上限と緊急停止を置きます。

    運用は、見える境界として実装する

    公開後の品質は、推薦ロジックだけでは保てません。権限、費用、案内文、計測の境界を製品の一部として扱います。

    利用制御

    相談 API の利用を制御する

    IP 単位の分・日上限、環境変数の緊急停止、タイムアウトを実装します。高頻度の正規利用とボット対策は、観測を踏まえて強化します。

    データ境界

    埋め込みを公開面から分離する

    RLS、embedding 非公開、サーバ権限の RPC、モデル名一致を組み合わせます。公開 UI は rice_catalog を通じて必要な情報だけを読みます。

    可観測性

    次に確認するのは、ページ型ごとの行動とエラーの輪郭

    GA4 と access_events では shop_click、consult_submit、revisit をページ型で分けます。Sentry DSN の確認を行い、相談 API のコストと失敗の兆候を同じ運用面で追えるようにします。

    ケーススタディの実行環境について

    この記録ページは単一 HTML と版付き CDN の GSAP、Lenis を使います。公開プロダクトは Next.js のビルド成果物です。SRI と CSP は展示ページの運用作業として扱い、公開プロダクトの安全設計とは分けて改善します。

    公開済み

    1.0.0 を公開

    カテゴリを広げるための進入条件

    少なくとも4週間、shop_click、consult_submit、revisit の信号とカタログ更新工数を観測します。画像認識や機器連携、桃、和牛、酒への展開は、米で運用の型を確認した後に評価する構想です。

    デリバリーの結論

    実験を、次の判断ができる形で公開した

    KomeSomme 1.0.0 は、味わい地図と相談 API を備えた米推薦サービスです。今回のデリバリーでは、推薦の根拠、技術選定、公開条件、次の観測を一つの運用可能な設計にまとめました。

    カタログを正本にする。 LLM は候補の順位を持たず、説明を補助します。

    採用と見送りを残す。 技術判断を、次の変更ができる条件と一緒に記録します。

    観測を次へ戻す。 購入導線、再訪、更新工数を同じ投資判断の入力にします。
