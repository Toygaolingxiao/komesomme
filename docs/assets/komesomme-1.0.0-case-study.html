案件の進め方

背景から公開判定までを横並びにし、前工程の成果が次工程の入力になる関係を示します。

1 · 課題定義

スコープの境界

店頭や通販では産地・価格・還元率が並びますが、甘みや粒立ち、おかずとの相性は比較可能な形になっていません。同心円は「どこに集中し、何を捨てたか」を示します。

模倣しにくい点は第1環に置いています。味わい・料理・酒の相性に加え、「合わない組み合わせ」まで人手で整理した一次データが、モデル丸投げでは得られない差になります。

2 · プロダクト概念

利用者が触る体験

画面は和紙の味わい地図として見せ、ベクトル検索は裏側に置きます（docs/08）。横軸は甘み、縦軸は粒感です。

味わいの盤面甘みと粒感の二次元盤。探針で好みの位置を指す
侍米師上位四銘柄と短い案内文を返す
二本立て座標探索は端末内。相談だけサーバ経由
購入通販とふるさと納税への導線

デモ：探針が銘柄付近をなぞります（座標は固定）

ほどける 粒立ち すっきり 甘みふくよか

各銘柄の座標はカタログ上の固定値です。動くのは探針だけで、近い四銘柄を本番と同じ粒度で強調します。

3 · 技術選定

レイヤー別のトレードオフ

上から画面、下へデータと商流。各層で左が採用、右が破線の見送りです。データ投入は Node（tsx）、銘柄カタログの正本は Git に置いています。

モデル混在や別 API サーバを見送ったのは、類似度の一貫性と一人運用の境界を守るためです。層が分かれて見えるほど、混在コストが読み取れます。

4 · 処理設計

レイヤ別のデータフロー

画面・サーバ・データベース・外部モデルの役割分担と、地図／相談の二系統を示します。

灰の点線：地図 橙の実線：相談 金の線：任意の一言 橙の破線：一言なしでも候補を返す

5 · 実装と公開

品質ゲートのパイプライン

段階はベルトのように繋がっています。菱形の Gate を満たさないと、次の箱へ進めません。

公開時の運用条件

  • · CI で lint・型検査・試験・ビルドを通す
  • · 本番は origin/main からデプロイする
  • · 埋め込みと照合 RPC は一般公開しない
  • · 相談 API には日次上限と緊急停止を入れる

一人体制での進め方

  • · 判断根拠は docs と Cursor rules に残す
  • · 未計測の効率指標は記載しない
  • · 設計から公開までを閉じ、文書と CI を再現可能な形で残す

7 · ロードマップ

1.x 以降の計画

近い順は、米の型完成（Phase 2）→ 再訪（Phase 3）→ その先の製品マトリクス構想。横展開は米のループが回ってから考えます。

Phase 2 · 米の型を完成

見つかって、比べて、買えるところまで通します。露出と転化の playbook です。

  • · 料理・シーン別の入口
  • · 銘柄比較と「向かない」
  • · SEO と内部リンク
  • · 比較後の直リンクと CTA
  • · 季節面 · 人手の特集

Phase 3 · 再訪

一度選んだ人が、また戻ってこられるようにします。横展開の前に、米のループを閉じます。

  • · 診断結果の共有 URL
  • · share card と OG
  • · LINE 公式への導線
  • · 再訪率を測れるようにする

構想 · 製品マトリクス

桃Somme / 和牛Somme / 酒Somme。同じエンジンの横展見通しです。Phase 2–3 のあとに検討します。

  • · 共通: 盤面 · 相談 · 事典 · 出口
  • · 差し替え: 軸と一次データ
  • · 未確約: 画像認識 · 機器連携

順序を取り違えないこと。再訪より先に製品マトリクスへ進むと、まだ閉じきっていない米の型を複製することになります。

まとめ

インタラクティブな味わい地図と相談 API は表層です。見送った選択肢と公開条件が、同じリポジトリに残っていることが、この事例の要点です。
