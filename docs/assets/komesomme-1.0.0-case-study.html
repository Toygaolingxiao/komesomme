DELIVERY LAB · 技術実験の記録

KomeSomme

味わいを、選べる形にする

米の銘柄を「産地・価格」だけでなく、「甘み」「粒感」「料理との相性」から選べるようにするための推薦サービスです。

これは、意味検索と決定的な推薦を一つの体験にまとめる技術実験です。構想、設計、実装、データ整備、公開判定までを一人で進めました。

01 問い味の言葉を比較可能にする
02 判断候補はデータと規則で決める
03 次の観測使われ方を公開後に測る

この事例で示すこと

  • 一人で構想から公開判定までを完了したこと
  • 技術選定とスコープの判断を文書化したこと
  • LLM に候補決定を任せないこと
  • 実験結果と、まだ測っていない利用結果を分けたこと

0 · プロジェクトの進め方

背景から公開判定まで

背景整理から公開判定までを一連の流れとして扱いました。公開後の利用状況は、次の課題定義に戻す前提です。

1 · 課題定義とスコープ

今夜の料理や好みに合う米を選ぶ

店頭や通販では産地・価格・還元率が並びますが、甘みや粒立ち、おかずとの相性は比較可能な形になっていません。同心円は「どこに集中し、何を捨てたか」を示します。

第1環は現時点の特徴です。Git 管理の構造化カタログ（相性・向かない組み合わせ）を人手で積んでいます。完成された参入障壁ではなく、更新を止めれば運用負債になります。

2 · プロダクト体験

味わい地図と相談

画面は和紙の味わい地図として見せ、ベクトル検索は裏側に置きます（docs/08）。横軸は甘み、縦軸は粒感です。

ChatGPT に「カレー向きの米は？」と聞く差は、言語の上手さではありません。こちらは構造化した味覚・相性・向かない組み合わせを正本に持ち、比較できる UI と買う出口までつなぎます。LLM は案内文だけを担当し、候補の順位は決めません。

味わいの盤面甘みと粒感の二次元盤。探針で好みの位置を指す
侍米師上位四銘柄。案内文は LLM、候補は規則と距離
二本立て地図は端末内。相談だけサーバ。結果は混ぜない
購入銘柄から通販・ふるさとへ。SKU 突合は未完

デモ：探針が銘柄付近をなぞります（座標は固定）

ほどける 粒立ち すっきり 甘みふくよか

各銘柄の座標はカタログ上の固定値です。動くのは探針だけで、近い四銘柄を公開サイトと同じ粒度で強調します。

3 · 独自性と商業上の位置づけ

構造化カタログが現時点の特徴

この実験の差分は、LLM に順位を預けず、根拠を持つカタログと比較 UI を先に置いたことです。

項目内容
想定利用者産地や価格は見られるが、今夜のおかずとの相性が比較できない人
片付ける仕事料理や口感の言葉から、候補銘柄を四つに絞る
いまの代替EC の人気順、価格・産地フィルタ、口コミ、汎用チャット
痛み味覚と「向かない」が表に出てこない
くさび二次元の味わい地図 + 相談 + 比較表 + 買う出口
現時点の特徴Git の構造化カタログ。LLM は事実と順位を持たない
収益アフィリエイト導線（楽天直リンク等）。成果突合は次フェーズ課題
見る指標推薦後の CTA、ページ型別 shop_click、再訪（計画）
銘柄と SKU推薦は銘柄単位。袋の産年・精米日までは保証しない

データ境界（銘柄近似）

定義

甘み・粒感はカタログ上の相対座標。相性は料理タグと人手メモ。向かない組み合わせも同じ正本に置く。

覆わないこと

産年バッチ、精米日、炊飯器、水量、浸水。銘柄級の近似であり、SKU 級の味保証ではない。

更新

正本は Git。validate:rice で必須フィールドと範囲を検査し、公開銘柄は 80 件以上。埋め込みは同一モデル版で全量再計算する。

人手カタログは短期の特徴にも、メンテ負債にもなります。カテゴリ展開の前に「銘柄 100 件あたりの工数」を見積もる前提です。

5 · 技術選定

レイヤー別のトレードオフ

上から画面、下へデータと商流。各層で左が採用、右が破線の見送りです。データ投入は Node（tsx）、銘柄カタログの正本は Git に置いています。

モデル混在や別 API サーバを見送ったのは、類似度の一貫性と一人運用の境界を守るためです。

埋め込み切替の原則

Gemini 既定 / OpenAI 切替はどちらも 1536 次元です。次元が同じでもベクトル空間は別物です。docs/04 の embedding_model で版を持ち、RPC はモデル名必須です。

  • · 問い合わせとカタログは、必ず同じモデル版で埋める
  • · provider を変えるときは seed で全量を入れ直す
  • · 異モデルのベクトルを同じ match_rice_profiles に入れない

6 · 推薦処理の設計

候補は距離と検索、文は LLM

地図経路と相談経路は分けて扱います。二つの経路を無理に混ぜず、入力に応じて候補を決めます。1.0.0 では diversity rerank は未実装で、近い候補が似る可能性は残ります。

経路候補の出し方順位の決め方出力
地図甘み・粒感の二次元距離（端末内）近い順。多様性なし上位四件。文言なし
相談銘柄名ヒット、または埋め込み → pgvector類似度（モデル版でフィルタ）上位四件 + 理由 + 案内
相性整理レイヤーなし順位は変えないカード理由文（決定的）
案内文なしLLM は説明のみ失敗しても上位四件は返す

相性整理レイヤー（料理相性ルール）

相談文と銘柄から、カード用の理由文を決定的な規則で組み立てる層です。候補の順位は埋め込み（または銘柄名ヒット）が先に決めます。LLM はこの規則にも順位にも関与しません。案内文が失敗したときの退避にも使います。

場面地図相談どちらが正か
探針だけ動かす座標の上位四件使わない座標
一文だけ送る使わない意味検索の上位四件相談
相談のあと地図が寄る1 位付近へ移動（表示）相談結果が先相談。地図は追従

地図推薦と相談推薦の一致率は、まだ公開していません。必要になった段階で、ログと人手評価によって確認します。

8 · 実装と公開判定

段階ごとの公開条件

段階はベルトのように繋がっています。菱形の Gate を満たさないと、次の箱へ進めません。

公開時の運用条件

  • · CI で lint・型検査・試験・ビルドを通す
  • · 公開環境は origin/main からデプロイする
  • · 埋め込みと照合 RPC は一般公開しない
  • · 相談 API には日次上限と緊急停止を入れる

一人体制での進め方

  • · 判断根拠は docs と Cursor rules に残す
  • · 未計測の数値は成果として書かない。仮説と判断基準を先に置く
  • · 初期公開条件はアクセス可能と安全側。次フェーズで週次の計測運用へ

9 · 脅威と運用上のリスク

公開サイトと、この HTML は別物

本ページはケーススタディ表示用の HTML であり、CDN 上の Tailwind / GSAP / Lenis / フォントを利用しています。実際の公開サイトは Next.js のビルド成果物です。以下は公開サイト側のリスクを主に書きます。

リスクいまの制御（粒度）残る穴次
相談 API の乱用IP 単位の分・日上限 · 環境変数の緊急停止 · タイムアウトIP ローテで迂回されうる必要時にボット対策
プロンプト注入LLM は候補を決めない案内文の汚染出力スキーマと監視
データ漏洩RLS · 埋め込み非公開 · RPC はサーバ権限 + モデル名一致権限設定ミス権限テストの継続
費用の暴走タイムアウト・緊急停止高頻度の正規利用コスト監視の計測確認（次フェーズ）
展示 HTML の CDN版付き URLSRI / CSP は未整備展示用途のまま明示

公開判定では、アクセス可能であることと主要機能の安全側を優先しました。GA4 / Sentry / access_events を週次で運用する状態にはまだ到達していません。アクセス可能と可観測は分けて扱います。ログ方針や CSP の実装粒度は本資料では省略します。

12 · ロードマップ

米カテゴリ内で運用手順を固める

近い順は、米の運用手順を閉じる（Phase 2）→ 再訪（Phase 3）→ 将来的なカテゴリ展開の仮説。進入条件を満たす前に構想を約束しません。

Phase 2 · 運用手順を閉じる

見つかって、比べて、買えるところまで。完成の目安は /pair と /compare、CTA 可測、ページ型の漏斗です。

  • · 料理・シーン別の入口
  • · 銘柄比較と「向かない」
  • · SEO と内部リンク
  • · 比較後の直リンクと CTA

Phase 3 · 再訪

横展開の前に、米のループを閉じます。再訪が測れてから次を考えます。

  • · 診断結果の共有 URL
  • · share card と OG
  • · LINE 公式への導線
  • · 再訪イベントが見えること

構想 · 将来的なカテゴリ展開の仮説

桃 / 和牛 / 酒などは仮説です。Phase 2-3 の観測と、専門家データ、軸の再定義が揃うまで着手しません。

  • · 進入: 4 週の観測で信号が続く
  • · 進入: 銘柄追加の工数が見積もれる
  • · 未確約: 画像認識・機器連携
進入条件（時間つき）まだ置かないもの
少なくとも 4 週間、shop_click / consult_submit / revisit のいずれかが継続的に発生し、かつカタログ更新工数が見積もれたあと。費用が収益仮説を壊さないこと サンプル不足の絶対 MAU・CVR 目標。達成前のカテゴリ横断の約束

順序を取り違えないこと。再訪より先にカテゴリ展開すると、閉じていない運用を複製します。

結論

派手さではなく、判断を残す

KomeSomme は、味わい地図と相談 API を備えた米推薦サービスです。見せたいのは、インタラクションの派手さではなく、実験を安全に公開し、次の判断につなげる設計です。

要点 1

候補決定を LLM に任せず、構造化されたカタログを正本にしたこと

要点 2

技術選定、見送った選択肢、公開条件を文書化したこと

要点 3

実験の証拠と、公開後に測る利用結果を分けたこと

現時点の KomeSomme は、技術実験を公開可能な形にしたプロダクトです。 課題定義、スコープ設計、データ構造、推薦処理、公開運用の境界を一人で組み立てました。

次の段階では、実際の利用データをもとに、推薦後の行動、購入導線、再訪、データ更新コストを検証します。商業化は、その観測から判断します。
