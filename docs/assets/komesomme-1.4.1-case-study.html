KomeSomme

味わいを、選べる形にする

米の銘柄を、産地や価格ではなく「甘み・粒感・料理との相性」から選べる推薦サービスです。約4週間の単独開発で、構造化カタログ、推薦ロジック、LLM案内、公開運用までを一体で構築しました。

0・PJ概要

制約のなかで、何を一気に通したか

単独開発・約4週間。在庫と配送は持たず、味覚データと推薦、公開運用までを閉じる範囲に収めました。専用ベクトル基盤の性能より、実装速度・権限管理・運用の単純さを優先しています。

制約

  • ・体制は単独開発。画面と相談 API を別サーバーに分けない
  • ・銘柄規模は百前後。権限とメタデータを同一 DB に置く
  • ・在庫・発送・問い合わせ対応は現段階で担わない
  • ・未測定の利用指標を成果として語らない

通した範囲

  • ・構造化カタログ（Git）→ validate → seed → Supabase
  • ・味わい地図（端末内順位）と相談（埋め込み検索）
  • ・事典（claims + URL）・料理別 /pair・購入導線
  • ・validate → CI → smoke → Production の固定手順

6・処理の流れ

レイヤー別データフロー

地図は一覧を取得したあと、端末内で順位を付けます。相談のみサーバー側で埋め込みと検索を行います。

灰色の点線：地図（一覧取得＋端末内順位） 橙色の実線：相談 金色の線：任意の案内文 橙色の破線：案内文の生成に失敗しても候補を返す

7・推薦設計

LLM に任せる領域、任せない領域

候補は距離計算と検索で決め、文章はLLMで生成します。地図は端末内計算、相談はサーバー側の埋め込み検索で処理します。

相性整理レイヤーは理由文だけを組み立て、順位は変えません。案内文の生成に失敗しても候補は返します。

8・公開ゲート

本番公開までの4つの手順

約4週間の単独開発で、1.0.0 から 1.4.1 まで、公開ごとに同じ手順を通しています。

G1・データ検査 — validate:rice

G1 データ
G2 検査
G3 手動

G1・データ

カタログの整合性を担保する

Git上で管理する銘柄の一次データを validate:rice で検査します。必須項目とスコア範囲。件数不足があれば、この段階で停止します。

npm run validate:rice

G2・検査

main 反映前に自動検査で止める

lint・typecheck・unit・e2e・client-bundle。シークレットの混入やクライアントバンドルの肥大化も、人手レビュー前に検出します。

CI · lint / type / unit / e2e / client-bundle

G3・手動

本番反映後に手動確認し、実施日を記録する

地図・Top4・購入導線。自動化で拾いきれない箇所を手動で確認し、smoke-test の記録に日付を残します。

smoke-test 記録

G4・公開

同一コミットでバージョンを更新してリリースする

VERSION・package.json・changelog を同一コミットで更新します。origin/main への反映が Vercel Production へのデプロイにつながります。

git push origin HEAD

埋め込みと照合 RPC は一般公開しません。相談 API には日次上限と緊急停止があります。本番のあとに smoke-test へ日付を残し、未計測の数値は成果として記載しません。
